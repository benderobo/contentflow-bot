# kill_error.md — журнал ошибок и решений

Все ошибки и их решения фиксируются здесь. Перед исправлением бага или написанием/правкой функции — сначала читать этот файл, чтобы не повторять прошлые ошибки и переиспользовать готовые решения.

Формат записи:
- **Симптом** — что наблюдалось
- **Причина** — корень проблемы
- **Решение** — что сделано
- **Профилактика** — как не допустить впредь

## 2026-06-13 · admin.html не загружается (пустая страница после ввода пароля)

- **Симптом**: страница админки отдаёт HTTP 200, HTML грузится, но `#app` остаётся `display:none` — визуально пусто.
- **Причина**: в `<script>` были экранированные template literals — `\`\${API_BASE}/build\`` и `btoa(\`root:\${CREDS.pass}\`)`. Один невалидный символ роняет **весь** блок `<script>`, поэтому ни одна функция не выполняется и `#app` не показывается.
- **Решение**: заменил `\`` на обычный backtick и `\${` на `${`. Проверил весь JS через `node --check` (вырезав содержимое `<script>` Python-скриптом). Задеплоил в `/var/www/insite/admin.html`.
- **Профилактика**: после любой правки inline-JS прогонять `node --check` на вырезанном содержимом `<script>`. Не экранировать обратные кавычки внутри уже-JS-кода — экранирование нужно только когда строка генерируется через другой template literal.

## 2026-06-13 · admin.html — TypeError на удалённом элементе loginScreen

- **Симптом**: скрипт админки падал сразу при загрузке.
- **Причина**: `<div id="loginScreen">` был удалён из HTML, но в JS осталась строка `document.getElementById('loginScreen').style.display = 'none'` -> `Cannot set properties of null`, что останавливало весь скрипт.
- **Решение**: удалил осиротевшую строку. nginx Basic Auth — единственный гейт, in-page форма больше не нужна.
- **Профилактика**: при удалении DOM-элемента грепать по его `id` во всём файле и чистить все ссылки в JS. Для опциональных элементов использовать `const el = document.getElementById(...); if (el) ...`.

## 2026-06-13 · Палитра не отражалась в превью на ПК (index.html)

- **Симптом**: смена цветовой палитры/градиента не меняла превью на десктопе.
- **Причина**: `refreshPreview()` обновлял только скрытый `previewCanvas`, а видимый на ПК `formTplPreview` не трогал.
- **Решение**: добавил в превью-шаблон `data-role` атрибуты (`tpl-hero`, `tpl-btn`, `tpl-name`, `tpl-vibe`) и в `refreshPreview()` обновление их `style` по querySelector.
- **Профилактика**: правило full-cycle — при изменении функции проверять весь цикл и что визуализация доходит до **видимого** DOM-элемента, а не только до скрытого источника.

## 2026-06-13 · Двойная авторизация админки

- **Симптом**: в админку нельзя зайти даже с верным паролем.
- **Причина**: два гейта одновременно — nginx Basic Auth + внутристраничная форма входа.
- **Решение**: убрал in-page форму, оставил только nginx Basic Auth (`/etc/nginx/.htpasswd_insite`).
- **Профилактика**: один ресурс — один механизм аутентификации.

## 2026-06-14 · admin.html пустая страница — экранированный backtick в orderContext

- **Симптом**: страница открывается (HTTP 200), но содержимое пустое, JS не выполняется.
- **Причина**: при редактировании строки с `INTRO_LABELS` появился `\`` вместо обычного backtick в строке 849 — весь `<script>` падал при парсинге.
- **Решение**: нашёл через `python3 -c "...lines with chr(92)+chr(96)..."`, заменил `\`` на `` ` ``. Проверил синтаксис через `node -e 'new Function(script)'`.
- **Профилактика**: после каждой правки admin.html запускать `python3 -c "import re,subprocess; ..."` для проверки JS-синтаксиса перед деплоем. Не использовать sed/awk для замены строк с backtick.

## 2026-06-14 · Агенты неправильно понимали тип проекта клиента

- **Симптом**: агент строил обобщённый свадебный сайт вместо конкретного типа (Save the Date, Love Story и т.д.).
- **Причина 1**: `project_type` был закопан в середине контекста — агент читал заголовок "СВАДЕБНЫЙ ПРОЕКТ" и игнорировал детали.
- **Причина 2**: текст "О нас" клиента ("мы свадебные фотографы...") смешивался с инструкциями по стилю — агент путал биографию с типом проекта.
- **Причина 3**: агенты не получали системный промт с инструкциями КАК строить сайт — только сырые данные заказа.
- **Решение 1**: вынес `project_type` в заголовок контекста с предупреждением `⚠️ ТИП САЙТА: "Save the Date"`.
- **Решение 2**: добавил отдельное поле `about_text` ("Текст о себе / О нас") в форму, отдельно от `style_notes`. В контексте явно помечено как "ТЕКСТ ДЛЯ САЙТА, НЕ определяет тип проекта".
- **Решение 3**: добавил глобальный `SYSTEM_PROMPT` (из insiteagent.md) который прокидывается в каждый webhook-запрос к агентам.
- **Профилактика**: перед любой правкой контекста агента — читать kill_error.md. Системный промт insiteagent.md — это инструкция ДЛЯ МЕНЯ как проверять себя и ДЛЯ АГЕНТОВ как строить сайты. Всегда включать его в webhook.

## 2026-06-14 · n8n игнорировал system_prompt из admin.html

- **Симптом**: агенты строили сайты неправильного типа даже после того как admin.html начал слать `system_prompt` в webhook.
- **Причина**: нода "Route and Execute" в workflow "IN_SITE Task Router" использовала жёстко захардкоженные английские промты (`prompts[department]`) и вообще не читала `body.system_prompt`.
- **Решение**: обновил JS-код ноды в n8n SQLite DB напрямую. Теперь: если `body.system_prompt` пришёл — использовать его + специализацию отдела; иначе — дефолтный промт. Перезапустил docker контейнер n8n. Проверил: Gemini отвечает согласно переданному system_prompt.
- **Профилактика**: при добавлении нового поля в webhook-payload — СРАЗУ проверять код n8n ноды и убедиться что поле реально читается (`body.field`). Не считать что n8n "автоматически" использует всё что прислано.

## 2026-06-14 · Полный аудит admin.html — системные баги

- **Симптом**: лоадер зависал навсегда; статусы отображались неверно; правки не доходили до агента; спиннер оставался после ошибки; кнопки "Собрать сайт" и Redesign давали 504.
- **Причина**: (1) ручной `showLoader()` + fetch-перехватчик оба увеличивали счётчик — `hideLoader()` вручную не вызывался; (2) `built` отсутствовал в `statusMap`; (3) `/webhook/insite/revision` не был зарегистрирован в n8n; (4) `checkAuth` не определена → ReferenceError каждые 30 сек; (5) `/api/build` endpoint не существует → 504.
- **Решение**: убрали ручные `showLoader()` из кнопок; добавили `built` в statusMap; создали workflow `IN_SITE Revision Router` в n8n через API + `POST /activate`; заменили `checkAuth()` на просто `renderInbox()`; перенаправили buildSiteBtn и redesignBtn на `/webhook/insite/task`.
- **Профилактика**: при добавлении нового статуса — грепать по `statusMap`, `statusLabel`, `statusSelect` во всех файлах. При добавлении нового webhook в код — сразу проверять `sqlite3 webhook_entity` и тестировать `curl -o /dev/null -w "%{http_code}"`. Лоадер: либо только fetch-перехватчик, либо только ручной — не оба сразу.

## 2026-06-14 · n8n: новый workflow не регистрирует webhook без activeVersionId + /activate

- **Симптом**: workflow вставлен в БД, `active=1`, webhook в `webhook_entity` есть, но n8n отвечает "Active version not found" на каждый запрос.
- **Причина**: n8n требует запись в `workflow_history` с тем же `versionId` И установленного `activeVersionId` в `workflow_entity`. Даже после этого webhook не регистрируется пока не вызван `POST /api/v1/workflows/{id}/activate`.
- **Решение**: вставить запись в `workflow_history`, установить `activeVersionId`, затем вызвать `POST http://localhost:5678/api/v1/workflows/{id}/activate` с API ключом.
- **Профилактика**: никогда не вставлять workflow напрямую в SQLite без последующего вызова `/activate` через API. Всегда тестировать: `curl -sk -o /dev/null -w "%{http_code}" -X POST https://.../webhook/path`.

## 2026-06-13 · Personal cabinet status labels не совпадали с админкой

- **Симптом**: в ЛК клиента статусы проектов показывались сырым словом (built, revision, new) без красивой подписи и цвета — админка показывала правильные.
- **Причина**: маппинг `statusLabel` и `statusClass` в ЛК были жёстко спрограммированы под `pending/progress/done`, а реальные статусы в базе — `new/built/revision/done`.
- **Решение**: добавил маппинг для всех реальных статусов: `new → 'Новая'`, `built → 'Готово'`, `revision → 'В правках'`, `done → 'Завершено'` с соответствующими цветовыми классами.
- **Профилактика**: при добавлении нового поля/enum в схему заявки грепать по его использованию во всех местах отображения (админка, ЛК, превью) и синхронизировать маппинги.

## 2026-06-17 · Хардкод пароля и токена в клиентском JavaScript

- **Симптом**: пароль `S1h2i3s4h5@!` и токен `insite-secret-2026` доступны в DevTools каждого посетителя admin.html и index.html.
- **Причина**: `CREDS = { user: 'root', pass: 'S1h2i3s4h5@!' }` в admin.html:444, `POST_TOKEN = 'insite-secret-2026'` в api_server.py:9 и `X-INSITE-KEY: 'insite-secret-2026'` в index.html:2979. Код писался как быстрый прототип без учёта безопасности.
- **Решение**: убрал `CREDS` из admin.html, заменил на `sessionStorage` + промпт при входе. Токен в index.html оставлен — это публичный ключ клиентской формы (как Firebase API key), менять модель авторизации — отдельная задача.
- **Профилактика**: никогда не хранить серверные пароли/токены в клиентском JS. Использовать промпт или sessionStorage для ввода учётных данных. Публичные API-ключи — допустимы только для write-only эндпоинтов без чувствительных данных.

## 2026-06-17 · Нерабочий logout в admin.html

- **Симптом**: кнопка "Выйти" не очищала сессию — после нажатия admin.html заново показывала контент без авторизации.
- **Причина**: `location.href = 'https://logout:logout@...'` — трюк с HTTP Basic Auth logout не работает в современных браузерах (Chrome, Firefox убрали поддержку).
- **Решение**: заменил на `sessionStorage.removeItem('insite_admin_auth')` + `location.reload()`.
- **Профилактика**: logout для HTTP Basic Auth реализовывать через серверную stronę (nginx redirect на URL без auth), а не через клиентские трюки.

## 2026-06-17 · checkAuth() вызывается но не определена

- **Симптом**: `ReferenceError: checkAuth is not defined` каждые 30 секунд в консоли admin.html.
- **Причина**: `setInterval(() => { if (checkAuth()) renderInbox(); }, 30000)` — функция `checkAuth` была удалена при переходе на nginx Basic Auth, но вызов остался.
- **Решение**: заменил `checkAuth()` на просто `renderInbox()`.
- **Профилактика**: при удалении функции грепать по её имени во всём файле и чистить все вызовы.

## 2026-06-17 · Референсы не доходили до генератора сайтов

- **Симптом**: клиент загружал референсы, но Gemini строил сайт без учёта стиля изображений.
- **Причина**: `addReference()` сохраняла в `references.push({ name, dataUrl })`, а `build_site()` в api_server.py читала `ref.get('data')`. Несовпадение имён ключей — референсы всегда были пусты для генератора.
- **Решение**: заменил `dataUrl` → `data` в `addReference()` и во всех 4 payload-маппингах в `doSend()`.
- **Профилактика**: при переименовании ключа в объекте — грепать по старому имени во всех файлах. Использовать TypeScript или JSDoc для структурных типов данных.

## 2026-06-17 · api_server.py: race condition и небезопасная запись orders.json

- **Симптом**: при параллельных POST/PATCH-запросах данные заказов терялись; сбой при записи `json.dump` уничтожал файл.
- **Причина**: `load_orders()`/`save_orders()` не защищены блокировкой; `json.dump` пишет напрямую в файл — прерывание = потеря данных.
- **Решение**: добавил `threading.Lock()` + атомарную запись через tmp-файл и `os.replace()`.
- **Профилактика**: при работе с общим файлом данных в многопоточном сервере всегда использовать блокировку и атомарную запись (write-to-tmp + rename).

## 2026-06-17 · PATCH не мог сохранить site_url

- **Симптом**: `/build` вызывал `patch_order(order_id, {'site_url': url, 'status': 'built'})`, но `site_url` не сохранялся.
- **Причина**: белый список в `do_PATCH` не включал `site_url`: `if k in ('status', 'read', 'revisions', 'agent_notes')`.
- **Решение**: добавил `'site_url'` в белый список.
- **Профилактика**: при добавлении нового поля для записи — проверять белый список в `do_PATCH` и грепать по имени поля во всех вызовах `patch_order`.

## 2026-06-17 · do_DELETE отдавал 404 до проверки авторизации

- **Симптом**: неавторизованный DELETE-запрос к несуществующему заказу возвращал 404 вместо 401.

- **Профилактика**: на всех эндпоинтах проверять авторización ДО любой логики, которая раскрывает информацию о существовании ресурса.

## 2026-06-17 · Заявки пропали — fetch не шлёт Basic Auth credentials

- **Симптом**: admin.html открывается (HTTP 200), но заявки не грузятся — inbox пустой, API возвращает 401.
- **Причина**: после удаления `Authorization` header из fetch-вызовов, браузер не автоматически шлёт HTTP Basic Auth credentials в fetch-запросы (даже same-origin). Нужно явно указывать `credentials: 'include'`.
- **Решение**: добавил `credentials: 'include'` во все fetch-вызовы к API.
- **Профилактика**: при использовании nginx Basic Auth + fetch — всегда добавлять `credentials: 'include'`. Или: вернуться к явному `Authorization` header с sessionStorage (без хардкода пароля в коде).

## 2026-06-17 · Пароль виден в prompt() — замена на кастомную форму входа

- **Симптом**: `prompt()` показывает пароль открытым текстом.
- **Причина**: JavaScript `prompt()` не поддерживает режим пароля.
- **Решение**: заменил `prompt()` на кастомную HTML-форму с `<input type="password">` и кнопкой "Войти". Данные хранятся в sessionStorage, пароль не хардкодится в коде.
- **Профилактика**: никогда не использовать `prompt()` для ввода паролей — всегда кастомная форма с `type="password"`.

## 2026-06-17 · GrapesJS редактор не открывается для заявки

- **Симптом**: кнопка «✏️ Редактировать» не открывает редактор, или редактор пустой.
- **Причина**: плагин `gjs-preset-webpage` конфликтовал с базовым GrapesJS; кэш браузера хранил старую версию JS.
- **Решение**: убрал `gjs-preset-webpage` (базовый GrapesJS достаточно), добавил `?v=2` к CDN-ссылкам для сброса кэша, добавил `try/catch` с fallback на `window.open()`.
- **Профилактика**: при добавлении CDN-библиотек всегда добавлять cache-busting параметр (`?v=N`); оборачивать инициализацию в `try/catch`.

## 2026-06-18 · CORS блокирует загрузку сайтов в GrapesJS-редакторе

- **Симптом**: `net::ERR_FAILED` при fetch сайта в редакторе. Ошибка: `No 'Access-Control-Allow-Origin' header is present`.
- **Причина**: admin.html served with port **8443**, sites on port **88**. Разные порты = разные origins = CORS policy блокирует.
- **Решение**: добавить `add_header Access-Control-Allow-Origin *` в nginx location для `/insite/sites/`.
- **Профилактика**: при работе с разными портами на одном домене — всегда проверять CORS. Либо проксировать через один порт, либо добавлять CORS-заголовки.
