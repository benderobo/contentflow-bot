**IP сменился с 91.149.238.201 на 167.17.180.42 (2026-06-03).**

Это **отдельный сервер**, не путать с VPN/xray-узлом `194.87.18.116` ([[server-194-87-18-116-justhost]]), который на 2026-06-02 был полностью мёртв в сети (null-route на JustHost). Пользователь ошибочно искал панель на `194.87.18.116`. Старый IP панели `91.149.238.201` — более не актуален.

**Случай 2026-06-02 «не заходит в панель»:** причина двойная — (1) отсутствие слеша в конце URL; (2) сертификат панели — Let's Encrypt, выписан на **домен**, а не на IP, поэтому при заходе по IP браузер ругается `NET::ERR_CERT_COMMON_NAME_INVALID`. Решение: либо принять предупреждение браузера, либо заходить по домену, на который выписан сертификат.

**Диагностический урок:** проверять доступность 3x-ui с этого хоста (`b`, `167.17.180.42`, дата-центр Cogent) ненадёжно — маршрут Cogent до сети `194.87.18.0/24` обрывается (`!N` network unreachable во Франкфурте), хотя с телефона (Happp, мобильный маршрут) сервер пингуется ~153 мс. ICMP/TCP-тесты с хоста `b` к серверам, отрезанным на магистрали Cogent, дают ложный «сервер мёртв».

**Случай 2026-06-03 «новая версия с SPA — логин даёт 403»:** панель обновлена до 3X-UI с React-SPA и CSRF-защитой. Любой POST (`/login`, API) без правильного токена → `403 Forbidden` с пустым телом. Механизм: GET базовой страницы кладёт в HTML `<meta name="csrf-token" ...>` (или endpoint `GET /<base>/csrf-token` → `{"obj":TOKEN}`), привязанный к session-cookie `3x-ui`; этот токен надо слать в заголовке `X-CSRF-Token`. Тогда `POST /<base>/login` с JSON `{"username","password","twoFactorCode":""}` → 200. **API инбаундов сменился на документированный `GET /panel/api/inbounds/list`** (старый `panel/inbound/list` → 404). **Настройки: `POST /panel/setting/all` (читать), `POST /panel/setting/update` (писать) — update требует ПОЛНЫЙ объект всех 78 полей, частичный payload валится на `gte` для webPort/subPort/sessionMaxAge/pageSize.**

**КРИТИЧНО — схема БД новой версии (Xray 26.6.1, проверено 2026-06-03):** клиенты хранятся в ОТДЕЛЬНЫХ таблицах `clients` (email,sub_id,uuid,password,auth,flow,security,total_gb,expiry_time,enable,tg_id...) + связка `client_inbounds(client_id,inbound_id,flow_override)`. `config.json` (`/usr/local/x-ui/bin/config.json`) генерится ИЗ ЭТИХ ТАБЛИЦ, а JSON в `inbounds.settings` — лишь вторичный кэш для UI. **Правка `inbounds.settings` НЕ влияет на конфиг Xray** — менять надо `clients`/`client_inbounds`. БД: `/etc/x-ui/x-ui.db`.

**УТОЧНЕНИЕ (2026-06-03, при добавлении клиента `zoloto`):** генератор Xray-конфига читает `clients`/`client_inbounds`, НО **генератор подписок (`/sub/`, `/json/`) читает `inbounds.settings`**. Поэтому новый клиент должен быть в ОБОИХ местах: в `clients`+`client_inbounds` (иначе нет в Xray → не подключается) И в `inbounds.settings` (иначе подписка по его subId отдаёт ПУСТО). Рабочий рецепт добавления клиента: (1) INSERT в `clients`, (2) INSERT в `client_inbounds(client_id,inbound_id=2,flow_override='xtls-rprx-vision')`, (3) INSERT в `client_traffics(inbound_id=2,enable=1,email,...)` (email UNIQUE), (4) добавить тот же клиент с тем же uuid/subId в `inbounds.settings`, (5) `systemctl restart x-ui`. **Надёжный способ править БД руками:** `systemctl stop x-ui` → правки через python sqlite3 → `PRAGMA wal_checkpoint(TRUNCATE)` → `systemctl start x-ui`. Если править при ЗАПУЩЕННОМ x-ui, он перезапишет инбаунды своим состоянием из памяти при остановке (или не увидит изменения из-за WAL). На старте x-ui читает БД и генерит config.json.

**Flow:** клиентам ставить `flow=xtls-rprx-vision`. В БД у старых клиентов попадался `xtls-rprx-vision-udp443` — config нормализует его к `xtls-rprx-vision`, НО подписка генерит ссылку с `-udp443` → рассинхрон сервер/клиент = «коннект есть, трафика нет».
